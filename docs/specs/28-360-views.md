# 28 — Customer 360 · Unit 360 · Booking 360 · Project 360 header

## Purpose
p25 §20 screen architecture: the three twin screens; p37 §31.3 "Project 360 header everywhere, context retained across modules"; p5–6 §4.1–4.2 twins. Existing Customer 360 (basic) and unit detail are the base.

## Data
No new tables; composition endpoints over existing features. `recent_context` per user (last project, last entity) in `user_preference` for context retention.

## Rules
1. **Unit 360** tabs: Overview (hierarchy path, product, areas, facing, price, sale status, current booking link, Unit Readiness ScoreCard 14, flexibility 08), Progress (07 with history), Changeability (08 matrix), Specification (09 revisions/drawings), Customisations (18), QA & Snags (15), Handover (16), Documents (22 finals for this unit), Post-handover (30 passport, warranty), Activity (02). Physical fields editable only by Site/Admin.
2. **Customer 360** tabs: Profile (04 incl. residency, applicants across bookings, merge history), Bookings (list → Booking 360), Communications (29), Commitments (13, all bookings), Requests (18/30), Documents (22 KYC), Health (Customer Health score 31 with drivers; until 31: derived from check-ins + escalations + overdue), Activity.
3. **Booking 360** tabs: Overview (unit + customer + status + Booking Readiness 14 + Handover Readiness 14 + next actions 10), Journey (06 internal layer), Sales handover (17 packet), Payments (19 + 21 loan + 20 lines for this booking), Documents (22 generated + checklist), Legal & Registration (22/23), Customisations (18), Commitments (13), Communications (29), Handover (16), Activity.
4. **Project 360 header** (sticky on every module screen): project name/code, product mix, units sold/available, next-month forecast & actual-to-date (20), true-risk ₹ (19), handovers due 30 d (16), open material escalations (12), Unit Readiness average (14); each figure links to its list; project switcher (01) lives here; context (project + last entity) retained across navigation and sessions.
5. Field masking (01) applies on every tab; customer-visible flags are shown as badges so staff know what the customer sees.
6. Performance: each 360 loads in ≤ 3 API calls (composition endpoints), skeletons per tab; deep links `/units/:id?tab=…`.

## API
`GET /units/:id/360` · `GET /customers/:id/360` · `GET /bookings/:id/360` (overview payloads; tabs fetch their own feature endpoints) · `GET /projects/:id/header` · `PUT /me/context`.

## Screens
Three 360 pages with a shared layout (header card, tab bar, tab content), the Project 360 header component, breadcrumb (Portfolio › Project › Tower › Unit). 375 px: header collapses to key figures; tabs scroll horizontally.

## Acceptance
p25 §20 three screens exist with the listed tabs (Playwright per tab from seeded data) · p37 §31.5 t10 drill-back · rule tests 4–6.

## Depends on / Feeds
Depends on most features (tabs degrade to "Not yet available" placeholders with the owning spec named until they land). Feeds navigation for everything.

## Files
`services/api/src/views/360*.ts`, `apps/workspace/src/pages/unit/Unit360.tsx`, `apps/workspace/src/pages/customer/Customer360.tsx` (replace), `apps/workspace/src/pages/booking/Booking360.tsx`, `apps/workspace/src/components/Project360Header.tsx`, `apps/workspace/src/components/Breadcrumb.tsx`.

## Not in this feature
Any domain logic; content of tabs is owned by their specs.

## Build note (2026-09-06)

**Scope: backend only** (composition endpoints + tests), per this run's standing autonomous
mandate. `Unit360.tsx`, `Customer360.tsx`, `Booking360.tsx`, `Project360Header.tsx`, and
`Breadcrumb.tsx` are not built — flagged, not faked.

**Architecture: tab-manifest composition, not inline aggregation.** Rule 6's "≤3 API calls" is
satisfied by design: each 360 endpoint returns a rich Overview payload plus a `tabs` manifest
(`views/tabs.ts`'s `tab()`/`notYetAvailable()`) naming each tab's own already-built feature route
(06/17/19/21/20/22/23/18/13/16/02 for bookings; 07/08/09/18/15/16/22/30/02 for units). Tab
*content* stays owned by its owning spec, per this file's own "Not in this feature" line — the
360 endpoint never re-implements it. A tab whose owning spec isn't built (Communications, 29)
degrades to `notYetAvailable(key, label, "29 (not built)")` rather than a fake empty list.

**New lightweight queries written for real gaps in existing exports**, rather than guessing a
nonexistent export or widening another spec's function beyond its own contract: unit-level
product-mix/sold/available aggregates (no existing export); `action WHERE booking_id = $1` for
Booking 360's next-actions (`listActions` has no booking filter); per-entity Activity feeds on
`unit_id`/`booking_id`/`customer_id` (direct `event` columns, no join needed); `project_hierarchy_
node` path-walk for Unit 360's breadcrumb trail.

**Customer Health (rule 2) built as a real interim formula**, per this spec's own literal fallback
text ("until 31: derived from check-ins + escalations + overdue"): baseline 80, weighted by
check-in satisfaction average, open-escalation count, and overdue demand amount — UNCONFIRMED
weights (no PDF numbers given for the interim state), same class as 06/14's placeholder formulas.
The escalation driver joins `action.customer_id`, which exists on the table (`0009_actions.sql`)
and is populated by `createAction`'s own INSERT — not independently confirmed that every caller
passes a non-null value, so this driver may silently contribute 0 for some escalations; low
stakes inside an already-UNCONFIRMED formula.

**Role-gated partial data, not a whole-endpoint 403.** The Project 360 header sits behind
`STAFF_ROLES` (no dedicated `permission_matrix` module covers a cross-cutting composition read
like this — same documented gap class as 20's forecast and 25's Policy Studio, gated the same way
`getUnit` already is), but its two forecast figures are additionally gated to `FORECAST_READ_ROLES`
by checking `ctx.actor.roles` manually and returning `null` for those two fields only when the
viewer lacks access — the rest of the header stays available to every staff role.

**One real permission bypass, caught by advisor pre-merge, fixed before landing.** `getCustomer360`
and `getCustomerDocuments` were gated with `requireRole(STAFF_ROLES)`, matching `getUnit`'s own
precedent — but `customer_overview` and `customer_documents` are core `permission_matrix` modules
(SITE/FM are `READ_LIMITED`, i.e. below `READ`, on `customer_overview`; `NONE` on
`customer_documents`), and `STAFF_ROLES` includes SITE/FM. The fix routed *around* the matrix
rather than widening it — same failure family as spec 26's `customer_documents` READ→WRITE
widening, this time a bypass instead of an over-grant. Fixed by switching both to
`authorize(ctx, "customer_overview"/"customer_documents", "READ")`, matching the exact precedent
already set by `model/customers.ts`'s own `getCustomer()` (which gates the same fields at the same
level) — that precedent settles the `READ_LIMITED` question too: the codebase already treats
`READ_LIMITED` as insufficient for this exact view everywhere else, so blocking SITE/FM entirely
is consistent, not a new masking tier invented for this spec. `getCustomerActivity` was moved to
`authorize(ctx, "customer_activity", "READ")` as well, matching its own matrix row (all 9 role
columns `R`) — this narrows access relative to the old `STAFF_ROLES` gate by dropping CUSTOMISATION
(defaults `NONE` for `customer_activity`), which is matrix-derived and correct. Covered by a new
regression test seeding a `SITE` ctx and asserting both `getCustomer360` and `getCustomerDocuments`
reject it. `getBooking360`/`getBookingActivity`/`getUnit360`/`getUnitActivity`/`getProjectHeader`
keep `requireRole(STAFF_ROLES)` — no equivalent booking/unit-scoped matrix module exists, same gap
class as `getUnit`'s own precedent, not a bypass since there's no narrower rule to route around.

**One write-on-read bug, caught by advisor pre-merge, fixed before landing.** The Project 360
header's `unit_readiness_avg` originally called `computeUnitReadiness` once per unit in the
project — but that function unconditionally `INSERT`s a new `score_snapshot` row on every call
(pre-existing behaviour from 07/08, its own `store.ts` comment already names the gap: "this
codebase has no scheduler/event-debounce mechanism... compute-on-read is the honest substitute").
This header loads on every module screen (rule 4) and fans that out to N units, turning an
already-accepted per-unit-view cost into N unwanted writes on the single hottest path in the app —
the same write-on-read class advisor caught twice already at specs 16 and 27's landings. Fixed by
switching to `explainUnitReadiness` (same module, same `build()`/`previousValue()` computation,
same returned `value`, no `persistSnapshot` call) — zero writes per load, same live number. The N×
*read* cost (one live compute per unit) is unchanged and is the same already-documented shape as
27's `getPortfolio`; not a new concern, not optimised here.

**Test coverage is honest, not exhaustive.** 10 of 13 tests in `views.test.ts` are shape assertions
(`Array.isArray`, `toHaveProperty`) proving an endpoint returns a well-formed payload on seeded
data, not that every figure is numerically correct — same admission as 27's KPI `it.each` note.
Only the health-overdue-driver test, the forecast role-gating test, and the new SITE-permission
regression test assert actual behavior.

**Verification.** `npx tsc --noEmit` clean. Full suite: 96/97 files, 706/711 tests green — the 5
failures are `registration/registration.test.ts`'s pre-existing worker-pool timeout flake under
full parallel `vitest run` (confirmed unrelated to this spec: the same file passes 6/6 in
isolation; `registration/core.ts` was not touched by this build).

## Build note (2026-09-07, UI)

**Scope: the four frontend screens flagged missing above** — `Unit360.tsx`, `Customer360.tsx`
(replaced in place, see deviation below), `Booking360.tsx`, `Project360Header.tsx`, `Breadcrumb.tsx`

**File-path deviation from the spec's own list, deliberate.** `Customer360.tsx` stays at
`apps/workspace/src/pages/Customer360.tsx`, not moved to `pages/customer/Customer360.tsx` as this
file's own Files line says — `CrmQueue.tsx` imports it from that exact path (`import {
Customer360 } from "./Customer360"`), and moving it would be a same-slice rename of a call site
with no behavioural upside. `Unit360.tsx`/`Booking360.tsx` do live under `pages/unit/`/`pages/booking/`
as specced, since those are genuinely new files with no existing call site to preserve.

**Embed vs. summary-card decision, per tab — the generic `TabPanel` (an auto-column-picked table
or key/value reader, `three-sixty/TabPanel.tsx`) is the default for every tab; four tabs get a real
embedded component instead, because a purpose-built screen already existed for that exact
booking/unit/customer-scoped slice and TabPanel's generic table would have been a strictly worse
reimplementation of it:**
- **Activity** (all three screens) → the existing `ActivityFeed` component (`{entityType,
  entityId}`, calls `/api/audit`), not the 360 endpoints' own new `/…/activity` routes — it already
  has family filtering and human-readable event labels TabPanel doesn't attempt. The three activity
  endpoints (`getUnitActivity`/`getBookingActivity`/`getCustomerActivity` in `three-sixty/api.ts`)
  ended up unused by any caller and were deleted rather than left as dead exports (CLAUDE.md: no
  unused exports); the backend routes themselves are untouched (still real, just not this UI's path
  to activity data).
- **Commitments** (Booking 360 + Customer 360) → the real `CommitmentsSection` component (the same
  one Promise Ledger's own detail view uses), not TabPanel. On Booking 360 it's a normal tab. On
  Customer 360 it is **always visible, not tab-gated** — see the regression note below for why.
- **Sales handover / Legal & Registration / Handover** (Booking 360 only) → not tabs at all;
  three secondary buttons open the existing `HandoverPacketDrawer` / `CaseDrawer` (registration) /
  `HandoverCaseDrawer`, each already a portaled, purpose-built workflow surface. All three drawers
  stay mounted unconditionally with `bookingId={opening ? bookingId : null}` (never
  `opening && <Drawer/>`) per `Drawer.tsx`'s own JSDoc: `DrawerContent`'s `AnimatePresence` exit
  animation needs the instance to persist through the `open:true→false` transition.

**Which tabs resolve to real data vs. legitimately degrade, read directly from each view file's
own `tab()`/`notYetAvailable()` calls (not reconstructed from memory):**

*Unit 360* (`unit-360.ts`) — progress, changeability, specification, qa_snags, post_handover,
activity always resolve. customisations, handover, documents each resolve **only when the unit has
a current booking** (all three are booking-scoped by definition — customisations/documents keyed
off `booking_id`, handover's `handover_record` FK is `booking_id` not `unit_id`); with no booking
they degrade to a named reason ("18/22/16 (no booking on this unit yet — nothing to show)"). Found
and fixed one bug in this file: `handover` previously fell back to `tab("handover", …,
/api/units/:id)` when unbooked — marked `available: true` but pointed at raw unit JSON, not a
handover payload. Now correctly degrades like the other two booking-scoped tabs.

*Booking 360* (`booking-360.ts`) — journey, sales_handover, payments, legal_registration,
customisations, commitments, handover, documents, activity all always resolve (a booking always has
a unit and, functionally, a primary applicant by the time it reaches this screen). communications
resolves only if a primary applicant exists on the booking, else degrades with a named reason. One
stale comment found, not fixed (out of this slice's file list): this file's own header comment says
"Communications (29) isn't built yet" — 29 has since landed (`routes-communications.ts` is
registered in `server.ts`), so this tab is not a placeholder in practice; TabPanel renders real data
off it today.

*Customer 360* (`customer-360.ts`) — communications, documents (KYC), activity always resolve (same
"29 has landed" correction applies here too). `requests` is intentionally excluded from the
rendered tab list — its own manifest comment says why (`api` points back at the 360 endpoint
itself, since 18 has no multi-booking listing route) — and served instead from the already-fetched
`change_requests` array inline. No tab in this file currently degrades.

**A real regression, found by this session's full-suite-from-fresh-DB run, fixed before landing.**
The first draft of `Customer360.tsx` moved Bookings and Commitments behind tabs (a "Bookings" tab,
a "Requests" tab holding a lightweight inline commitments+change-requests list instead of the real
`CommitmentsSection`). That broke two already-passing e2e guards that assert both are visible
**immediately** after opening a customer, no tab click: `commitments.spec.ts`'s mobile-wrap
regression test (which creates a real commitment and measures its card geometry — 13's own
regression guard for a title/badge overflow bug found and fixed at that spec's landing) and
`journey.spec.ts`'s "View journey" wiring test (06's own guard that the button opens a real
`JourneyTimeline`, not a stub). Fixed by restoring both as always-visible sections above the tab
bar, matching the pre-28 file's own layout exactly (h2 "Bookings" + card rows with a "View journey"
button per booking that opens `JourneyTimeline` directly, plus a real `CommitmentsSection` per
booking) — additive to the new tabs, which now hold only genuinely new surface (Profile, Change
requests, Health, plus the manifest's communications/documents/activity). Confirmed no other spec
depends on the old "Bookings"/"Requests" *tab* structure — only the always-visible content.

Customer 360 now fetches commitments twice — once inside `getCustomer360`'s own payload (the
`commitments` array, no longer read by this UI) and once per booking via `CommitmentsSection`'s own
fetch. **This duplication is deliberate, not an oversight**: the embedded component is what
`commitments.spec.ts`'s mobile-wrap guard actually measures (a real `<Card>` rendered by
`CommitmentsSection`, not a synthesized `<li>`), so collapsing it back to the inline array would
silently re-break that guard the same way this build's first draft did.

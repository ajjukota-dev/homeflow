# 28 — Customer 360 · Unit 360 · Booking 360 · Project 360 header

## Purpose
p25 §20 screen architecture: the three twin screens; p37 §31.3 "Project 360 header everywhere, context retained across modules"; p5–6 §4.1–4.2 twins. Existing Customer 360 (basic) and unit detail are the base.

## Data
No new tables; composition endpoints over existing features. `recent_context` per user (last project, last entity) in `user_preference` for context retention.

## Rules
1. **Unit 360** tabs: Overview (hierarchy path, product, areas, facing, price, sale status, current booking link, Unit Readiness ScoreCard 14, flexibility 08), Progress (07 with history), Changeability (08 matrix), Specification (09 revisions/drawings), Customisations (18), QA & Snags (15), Handover (16), Documents (22 finals for this unit), Post-handover (30 passport, warranty), Activity (02). Physical fields editable only by Site/Admin.
2. **Customer 360** tabs: Profile (04 incl. residency, applicants across bookings, merge history), Bookings (list → Booking 360), Communications (29), Commitments (13, all bookings), Requests (18/30), Documents (22 KYC), Health (Customer Health score 31 with drivers; until 31: derived from check-ins + escalations + overdue), Activity.
3. **Booking 360** tabs: Overview (unit + customer + status + Booking Readiness 14 + Handover Readiness 14 + next actions 10), Journey (06 internal layer), Sales handover (17 packet), Payments (19 + 21 loan + 20 lines for this booking), Documents (22 generated + checklist), Legal & Registration (22/23), Customisations (18), Commitments (13), Communications (29), Handover (16), Activity.
4. **Project 360 header** (sticky on every module screen): project name/code, product mix, units sold/available, next-month forecast & actual-to-date (20), true-risk ₹ (19), handovers due 30 d (16), open material escalations (12), Unit Readiness average (14); each figure links to its list; project switcher (01) lives here; context (project + last entity) retained across navigation and sessions.
5. Field masking (01) applies on every tab; customer-visible flags are shown as badges so staff know what the customer sees.
6. Performance: each 360 loads in ≤ 3 API calls (composition endpoints), skeletons per tab; deep links `/units/:id?tab=…`.

## API
`GET /units/:id/360` · `GET /customers/:id/360` · `GET /bookings/:id/360` (overview payloads; tabs fetch their own feature endpoints) · `GET /projects/:id/header` · `PUT /me/context`.

## Screens
Three 360 pages with a shared layout (header card, tab bar, tab content), the Project 360 header component, breadcrumb (Portfolio › Project › Tower › Unit). 375 px: header collapses to key figures; tabs scroll horizontally.

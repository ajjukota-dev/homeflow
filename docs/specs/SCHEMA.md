# SCHEMA — ground truth from merged migrations (R0.5)

Generated by reading `services/api/migrations/0000_init.sql` through `0003_canonical.sql`
in full (2026-09-05). This is what the database **actually** looks like on `main` today —
not what any spec assumes. When a spec's `## Data` section is about to become real code,
diff it against this file first. Every drift found so far is logged in **§ Known drift**
below with the fix already applied to spec text (or the decision still open).

This file does not repeat every column of every table verbatim forever — re-generate the
affected section from the migrations whenever a new one lands, rather than trusting this
doc blindly once R1+ starts adding `0004_*.sql` onward.

## Real enums / vocabularies (as CHECK constraints or code, not spec prose)

- **`unit.sale_status`** (DB, lowercase): `available, held, booked, registered, handed_over, cancelled_release`. Spec vocabulary (`AVAILABLE`…) is a translation layer in `model/status.ts::toSpecUnitSaleStatus` — the DB was never renamed (documented cost: ~10 call sites).
- **`booking.status`** (DB, lowercase): `draft, confirmed, submitted, returned, crm_accepted, active, registered, handed_over, cancelled, transferred`. Same translation layer (`toSpecBookingStatus`/`toDbBookingStatus`), transition graph in `BOOKING_TRANSITIONS`. **`crm_accepted` is a legal DB value and a defined transition target, but no code path writes it today** — see drift #1.
- **`unit_progress.state_code`** (free text, no CHECK): code writes `not_started | in_progress | complete | verified` (matches `gates.ts`'s `ProgressState`).
- **`gates.ts::GateState`** (real, used by `deriveGate`): `OPEN | CLOSING | CONDITIONAL | EXCEPTION_ONLY | HARD_CLOSED` — **matches spec 08's five states exactly, no drift**.
- **32-module permission matrix** (`seed/permissions.ts`): `dashboard, customer_overview, customer_journey, customer_tasks, customer_documents, customer_financials, customer_loan, customer_legal, customer_registration, customer_unit_readiness, customer_snags, customer_commitments, customer_communications, customer_handover, customer_activity, customer_audit, sales_handover, documents, collections, loans, legal, registrations, unit_readiness, snagging, handovers, commitments, communications, escalations, approvals, notifications, comments, reports, administration`. **Module is `unit_readiness`, never `unit_progress`** — see drift #3.
- **Event registry** (`events/registry.ts`): Appendix B names + sanctioned extensions, each flagged `built: true/false`. `built:false` rows (e.g. `document.requested`, `loan.sanction_received`, `commitment.created`, `escalation.raised`, `handover.scheduled`, `warranty.case_opened`) are real future hooks for R1+ specs — not drift, just not wired yet.

## Known drift (found 2026-09-05, R0.5)

1. **Spec 06 rule 1** said a journey instantiates "On `booking.status → CRM_ACCEPTED`". The real `acceptBooking` (`bookings-crm.ts`) transitions `submitted → active` directly and never writes `crm_accepted` — confirmed by reading the function body. `crm_accepted` is a legal DB value (`booking_status_check`) and a graph edge in `model/status.ts`, but nothing produces it. **Fixed**: spec 06 rule 1 now triggers on the real, already-emitted event `sales_handover.accepted` instead of a status value nothing writes; a note tells 17's rebuild to either retire the unused `CRM_ACCEPTED` status value or start actually using it, and to keep 06 in sync either way.
2. **Spec 07** assumed `component_definition.name`; the real column is `label`. **Fixed** in spec text (kept `label`, dropped the invented `name`).
3. **Spec 07** assumed a permission module named `unit_progress`; the real module (in the 32-module matrix, already live behind R0.6's `authorize()`) is `unit_readiness`. **Fixed** in spec text.
4. **Spec 08** assumed `change_gate_rule` columns `trigger_state`/`trigger_event` where the real table has one column, `min_state` (a `ProgressState`, not a `GateState`); assumed `change_category.name` where the real column is `customer_label`; assumed `product_types[]`/`trade`/`default_lead_days` don't exist on either table. **Fixed** in spec text: renamed `name`→`customer_label` in the Data table, noted `min_state` as the real trigger column with `trigger_event` kept only for the non-progress triggers (procurement/drawing/handover events) that have no existing analogue, and flagged the new columns as additive.
5. Two stale code comments contradicted merged reality, and rechecking them surfaced a real gap:
   - `0001_identity.sql`'s `auth_event` comment said to fold into `event` "once 02 lands" — 02 has landed. **Fixed**: comment now gives the still-true reason to keep it separate (auth events aren't project/entity-scoped; `event`'s typed registry + append-only trigger don't fit free-form auth event types), not a stale "once X lands" promise.
   - `0002_event.sql`'s `event.actor_user_id` comment said it's nullable "because no user table exists yet" — 01 has landed, so I checked whether `appendEvent()` call sites now populate it. **They don't, anywhere** — grepped every domain handler (`bookings-crm.ts`, `tower-view.ts`, `warranty.ts`, `qa.ts`, etc.); none pass `actor_user_id`/`actor_kind` to `appendEvent`, so every real event today is stamped `actor_kind='SYSTEM'`, `actor_user_id=null` regardless of who actually acted — even though R0.6 put `ctx.actor` inside every one of those handlers. This is a real, verified gap, not just a stale comment. **Comment fixed** to state the gap plainly at the time; **Fixed (2026-09-05, P5 of the consolidation)**: `events/append.ts` now exports `actorFields(ctx)`, mapping `ctx.actor.kind` (`STAFF`→`USER`, `CUSTOMER`→`CUSTOMER`) to the event's `actor_kind`/`actor_user_id`; every one of the ~65 production `appendEvent()` call sites across 23 files spreads `...actorFields(ctx)` in (three functions — `setupFunding`, `raiseDemandsForUnit`, `insertUnit` — needed a new optional `actor` parameter to reach it). The one case with no live `ctx` (the post-commit `sales_handover.accepted → journey.instantiate` subscriber in `journey/subscribers.ts`) forwards the *triggering event's own* `actor_user_id`/`actor_kind` instead of defaulting to SYSTEM, so the async side effect still attributes correctly. Proven, not just asserted, by `events/actor-attribution.test.ts`: a real `createBooking`+`acceptBooking` call chain attributes every event it emits (including the post-commit `journey.started`) to the actual acting user. See TODO.md's R2.5 P5 row.

6. **Spec 21 (loans)** reuses the real `loan_case` table (`0000_init.sql`: `id, booking_id, lender, sanctioned_amount, status`), but its column names don't match the spec's. Unlike drift #2/#4 (ALTER, keep both names reconciled in spec text), this migration (0026_loans.sql) **renamed the columns in place**: `lender`→`lender_name`, `sanctioned_amount`→`sanctioned_amount_inr`, `status`→`stage` (with a new, richer stage enum replacing the old free-text default). Confirmed safe before renaming: grepped every reference to the old column names — only `seed.ts`'s own INSERT used them, and R2.5/R3's consolidation work (this session) hasn't deployed anywhere real yet, so there was no live data or downstream consumer to break. `seed.ts` was updated to the new names in the same slice. If a future rename candidate has any other consumer (a deployed environment, another module's query), ALTER-and-reconcile (07/08's pattern) rather than rename.

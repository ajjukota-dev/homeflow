# 10 — Universal Action

## Purpose
p8 §7: "Every actionable item — task, approval, follow-up, document request, exception, escalation — should normalize into one Action object." Fields (p8): id, type, title, source module, source entity, owner, backup owner, due date, priority, SLA policy, status, blocking reason, dependency, customer visibility, evidence requirement, escalation tier, auto-created vs manual. States (p8, App. A p41): **New, In Progress, Waiting Internal, Waiting Customer, Blocked, Ready for Approval, Closed, Cancelled**. "Evidence required for closure."

## Data
| Table | Columns |

## Rules
1. Single creation path `createAction(ctx, {type, source, …})` applies `action_type` defaults, derives `project_id`, starts an SLA clock (06) when actionable, emits `action.created`. All handshakes call it (see Sources).
2. Sources (auto-created): task instances (06; the task row references the action), CRM acceptance → onboarding actions (17), demand due/overdue → collections follow-up (19), reason-code missing → "record reason" (19), commitment at risk → owner action (13), snag raised → QA/contractor action (15), gate stale → verify action (07), document requested/rejected → customer document request (22/17), approval needed → approval action (18, 19, 22), intervention → owner action (27), warranty case → FM action (30), escalation → tiered action (12).
3. Transitions: `NEW→IN_PROGRESS` (owner acts), `IN_PROGRESS↔WAITING_INTERNAL|WAITING_CUSTOMER` (reason required; SLA pause if policy allows), `→BLOCKED` (reason + `depends_on_action_id` or blocking entity), `→READY_FOR_APPROVAL` (approval family), `→CLOSED` (evidence rule satisfied), `→CANCELLED` (reason; MANAGEMENT/SUPER_ADMIN or creator while NEW). Every transition logged.
4. Close is refused (`gate_blocked`) unless the evidence requirement is met: `VERIFIED_ATTACHMENT` needs ≥1 evidence with `VERIFIED` by a user ≠ uploader **[E §3.2 "evidence not verified"; self-verify guard keyed on submitter]**; `CHECKLIST` needs all required items; `APPROVAL` needs an approval by `approver_role` ≠ actor **[E self-approve guard]**; `EXTERNAL_REF` needs a reference.
5. Actions with `owner_user_id` null sit in the role queue; first claimer becomes owner (`claim`). Reassign keeps history and is blocked while `READY_FOR_APPROVAL` **[E 🐛 fix: no reassign-then-verify]**.
6. `customer_visible` actions surface in the portal as "Action required from you" with `customer_title` only (p18 §11 "actions required from customer").
7. Closing a source entity (e.g. snag closed, payment received) auto-closes its open actions with `close_note = "Resolved by <event>"` — idempotent subscriber on events (02).
8. Priority never overrides SLA: ranking (11) uses both; a CRITICAL action with no due date gets the type's default SLA.

## API
`GET /actions?owner=me|role|user_id&status&project_id&due_before&type` · `GET /actions/:id` (with transitions, evidence, checklist, source link) · `POST /actions` (manual) · `POST /actions/:id/claim|start|wait|block|unblock|submit-approval|approve|reject|close|cancel|reassign` · `POST /actions/:id/evidence` (presigned) · `POST /actions/:id/evidence/:eid/verify|reject` · `PUT /actions/:id/checklist/:item` · `GET /queues/:role` · `GET/PUT /action-types` (Studio).

## Build note (2026-09-06) — Action detail endpoint + Action drawer

**A real gap in a spec previously marked backend-complete:** this spec's own API list names `GET /actions/:id` (with transitions, evidence, checklist, source link) — it was never built. Filled now: `getAction()` in `services/api/src/actions/core.ts` (one query on `action` plus `Promise.all` over family/SLA-state/checklist/evidence/transitions — a wide join was rejected since the drawer opens on demand for a single action, not in a list's hot path) and its route `GET /api/actions/:id` in `routes-actions.ts`. This is a backend addition to an already-merged spec, not new scope — recorded here and in TODO.md's spec 10 row, which previously read as fully complete.

**Known gap, flagged not fixed:** rule 3's prose reads `IN_PROGRESS↔WAITING_INTERNAL|WAITING_CUSTOMER` as bidirectional, but `waitAction` in `core.ts` only ever moves *into* a Waiting state — there is no endpoint back to In Progress except `unblockAction` (Blocked→In Progress only). The drawer's `TransitionActions` does not fabricate a workaround (e.g. a fake "resume" button that silently calls something else); Waiting Internal/Customer can still reach Close, Cancel, or the other Waiting state, and the gap is documented in that file's own header comment.

**Real scope cuts, flagged not faked (`ActionDrawer.tsx` header comment):** "why it exists" renders `source_module`/`source_entity_type`/`source_entity_id` as plain text, not a link — no per-entity permalink/routing exists anywhere in this app (`nav.ts` is a fixed set of role tabs, not a URL-addressable entity viewer). Owner/backup render as raw user ids — no universal name-lookup endpoint is available to every actor (same gap already flagged in 11's Build note for Team view). No status stepper, despite the Screens line calling for one — the History section already shows the real transition path taken, including branches (Waiting Internal ↔ Waiting Customer) a linear stepper can't represent, so a second depiction was judged redundant rather than built to check a box. No evidence *upload* UI — verify/reject act on evidence rows the backend already has; the presigned-upload flow itself isn't wired here. Departmental queues (`Queues.tsx`) and the Studio tab (`studio/ActionTypes.tsx`) from this spec's Files list are not built in this slice — deferred to a follow-up slice.

**Real bug caught by advisor review before landing, fixed:** `TransitionActions` recomputed its button set from the `action` prop on every render, but after a transition posts successfully, the parent's refetch (`onChanged` → `load()`) is async — for the window between the POST resolving and the new detail arriving, the button set still reflected the *old* status. A fast second click (e.g. double-clicking Start) re-sent the same transition and hit the server's own conflict guard (`cannot start from In Progress`) as a confusing user-facing error on an action that had, in fact, already started successfully. Fixed with a `settling` state that disables the whole button group from the moment a transition fires until a new `action` object reference actually arrives (not a timer) — covered by a regression test that fires Start, then clicks it twice more before the refetch resolves, and asserts exactly one POST.

**The most significant finding in this slice — a documented gap this session's own earlier build note had already flagged as a pre-ship blocker:** `journey/instances.ts`'s header comment (written when 10's backend first landed) says plainly: a caller hitting a task-backed action's own routes directly (`POST /api/actions/:id/close|approve|cancel`) desyncs `task_instance`/the journey, and this "must be fixed... before that UI ships" — because `completeTaskInstance` is the only caller that keeps the two in sync, via a direct in-process call, not an event subscriber. Shipping the drawer *is* that UI. Confirmed the path is real, not hypothetical: `myday/core.ts`'s `ACTION_QUERY` has no filter excluding task-backed actions, so a task-backed action (e.g. a booking's PT1/T1/T6) surfaces in My Day like any other, and the drawer's `TransitionActions` would have offered Close/Approve/Cancel on it with no guard at all. Clicking Close would have returned 200, the action would go `Closed`, and `task_instance`/the stage roll-up would silently never move — a wrong-success failure, not a missing-capability one, and worse than every other gap flagged in this slice because it reports success while breaking state.

Fixed with the minimal correct scope (not the full `action.closed` subscriber rule 7 still owes — that would need re-entrant `closeAction`/`approveAction` calls from inside `completeTaskInstance`'s own open transaction, against this codebase's never-nest-`withTx` rule, the wrong thing to build at the end of a slice): `getAction` now returns `task_instance_id` (a real FK lookup, `task_instance WHERE action_id = $1`, not a derived flag) on `ActionDetail`. `TransitionActions.availableTransitions` hides Close/Approve/Cancel for a task-backed action and `ActionDrawer` shows a plain-text note ("This action completes through its journey task...") instead — Reject stays available since it only returns Ready for Approval to In Progress, nothing completes. Enforced server-side too, not just client-gated: `closeAction`/`approveAction` both already accept an optional `maybeTx` used only by `completeTaskInstance`'s internal call — `!maybeTx && isTaskBacked(...)` cleanly discriminates "external HTTP caller" from that one legitimate internal path and refuses with a named conflict; `cancelAction` takes no `tx` and has no internal caller at all, so it's guarded unconditionally. Regression tests added in `journey/instances.test.ts` (not `actions/core.test.ts` — building the task_instance FK chain needs the real `bookAndAccept`/journey-instantiation fixtures already there): direct `closeAction`/`cancelAction`/`approveAction` calls on a task-backed action all throw the new conflict, and `completeTaskInstance`'s own internal call to `approveAction` on the same action still succeeds — proving the guard keys on caller, not on the action merely being task-backed.

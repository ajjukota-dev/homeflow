### Deviations from the spec, and why

1. **`migrations/sql.py` exists.** asyncpg prepares every statement and a prepared statement may hold exactly one command, so `op.execute("CREATE TABLE a (…); CREATE TABLE b (…);")` fails with `cannot insert multiple commands into a prepared statement`. `sql()` splits a script on top-level `;` respecting `'…'` literals, `$tag$…$tag$` bodies and `--` comments. The alternative was several hundred one-line `op.execute` calls.
2. **`session` and `otp_challenge` are created in 0001 without the `customer_id` FK; 0002 adds it** (`_deferred_identity_fks`), together with the `project_id` FKs on `event`, `job` and `file_object`. This was the brief's explicit "your call".
3. **All customer policies in 0002 are created last**, in `_customer_policies()`, not inline via `partitioned(..., customer_via=)`. Every customer predicate joins through `booking_applicant`, and a policy cannot reference a table that does not exist yet. `rls(table, customer_via)` still works inline for 0003, where `booking`/`booking_applicant` already exist.
4. **`booking_applicant`'s customer policy matches `customer_id = _hf_customer_id()` directly** rather than the `booking_id IN (SELECT booking_id FROM booking_applicant …)` shape in technical 02 §3. That shape is self-referential and Postgres rejects it outright. Every other customer policy reaches the customer's bookings through this one, so behaviour is unchanged except that a customer does not see a co-applicant's own applicant row.
5. **`_hf_customer_id()` helper function.** `current_setting('app.customer_id', true)::uuid` raises `22P02` when the GUC is `''` (the anonymous case), which would make the anonymous path error instead of return nothing. The helper is `nullif(…, '')::uuid`, `STABLE`.
6. **`uuid_generate_v7()` fills `rand_a` with the sub-millisecond fraction** (RFC 9562 "replace leftmost random bits with increased clock precision") instead of leaving it random. Without it, ids from the same millisecond sort randomly and the 1000-row ordering test fails ~every run. The remaining 62 bits stay from `gen_random_uuid()`. A `# ponytail:` comment names the ceiling: no session counter, so two ids inside the same ~244 ns tick fall back to random ordering.
7. **RLS added to `event` and `file_object`** — technical 02 §4.2/§4.4 give both a `project_id` but show no policy, while §3 says RLS is on every project-partitioned table. §3 wins.
8. **`customer`, `team`, `component_definition`, `change_category`, `change_gate_rule` get a staff-realm policy with no project filter.** They are not project-partitioned (technical 02 §3: customer is cross-project; config tables are readable by all staff, writable only through `modules/admin`).
9. **`project`'s staff policy compares `id`, not `project_id`** — it *is* the partition key.
10. **Added `OWNER_DATABASE_URL`** to `settings.py` and `.env.example`, as the brief instructed.

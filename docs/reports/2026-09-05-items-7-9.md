## Item A — Frontend base (TASKS Vivek 8 · technical 09)

### Why

Item 1 deliberately left `apps/workspace` empty: v1's frontend is CRA + craco, and copying 2.4 MB
of unbuildable webpack config would have broken the root build for no gain. The whole of TASKS
Vivek 8 is that migration, so it starts here.

Three things had to become true at once (technical/09 §1–§4, §7):

1. **v1's 27 pages run on Vite** with their paths preserved, so bookmarks keep working and each
   page can be ported to TypeScript one at a time rather than in one unreviewable diff.
2. **The frontend stops holding a token.** v1 kept a JWT in `localStorage`, put it in an
   `Authorization` header, refreshed it on 401, and sent staff to `auth.emergentagent.com` to sign
   in. Technical/03 replaced all of that with an opaque `hf_session` cookie the server can revoke —
   but the browser was still speaking the old protocol, so nothing in the app actually worked
   against the 2.0 API.
3. **Colours, spacing, radii and type get one home.** v1 declared its palette in `src/index.css`,
   the customer app declared a different one in its own, and the customer app had two literal hex
   values in a gradient. `packages/ui/src/tokens.css` is now the only place any of it is defined
   (technical/09 §1, CLAUDE.md "design tokens only") — with the workspace values carried across
   verbatim, because the design decision at the top of `design-language.md` is still open and the
   instruction is not to restyle v1's screens.

### Benefit

- The internal app boots in **~15 s to a production build** instead of CRA's webpack, runs on a
  toolchain that is still maintained, and no longer pulls `react-scripts`, `craco` or a tarball
  from `assets.emergent.sh` into the dependency tree.
- **No token exists in JavaScript any more.** A stolen `localStorage` value used to be a
  permanent login; now there is nothing in `localStorage` at all (asserted in
  `apps/workspace/src/lib/auth.test.jsx`), and a leaked cookie is one `UPDATE session SET
  revoked_at` away from dead.
- **No third party is in the sign-in path.** The only route out of the sign-in screen is
  `/auth/google/start` on HomeFlow's own API. A Playwright test asserts the string
  `emergentagent` does not appear on the page.
- **One deployable.** `docker compose up -d --build` and `http://localhost:8001/` is the workspace,
  `http://my.localhost:8001/` is the customer app, same-origin with their API — no CORS, no second
  web server, no CloudFront.
- **A hard-coded colour now fails the build.** `npm run lint` errors on `bg-[#123456]` in new code
  (verified with a throwaway file) and warns on v1's 368 existing arbitrary lengths, so the debt is
  counted rather than invisible.
- The customer portal's identity comes from `/me/session`. The `?booking_id=` shape the
  spec forbids is not reachable — there is nothing to pass it to.

### Verified

`npm run build`, `npm run typecheck`, `npm run lint` and `npm test` pass for `packages/ui` and both
apps. The workspace runs all 27 of v1's pages on Vite against the `hf_session` cookie — Dashboard
and Customer 360 screenshotted with real data. The customer app renders the OTP sign-in as its front
door and reaches the code step. Both apps are served by the container by hostname with correct cache
headers, client-side routing falls back to `index.html`, `/api/*` still returns the JSON envelope,
and a `../` path escapes nothing. 15 Playwright tests pass at 1440 / 768 / 375 with zero console
errors (the expected 401 from `GET /me/session` on a sign-in screen is filtered, with the reason in
the spec file). `localStorage` is empty after a full sign-in cycle. Backend tests stay at 121.

### Not verified / known gaps

- **v1's Layout is desktop-only at 375 px** (`dashboard-375.png`). The sidebar does not collapse.
  CLAUDE.md and the design-language banner both say not to restyle v1's screens until the design
  decision lands, so this is recorded rather than fixed; it belongs to whichever slice ports the
  shell. The same is true of the header search field clipping at 768.
- **`/me/home` does not exist yet**, so the customer app's `Home` still cannot load — it is
  TASKS Vivek 15. The sign-in gate in front of it does work; behind it the page shows its error
  state, which is the honest thing to render.
- **A customer OTP session could not be exercised end to end.** `POST /auth/otp/request` returns
  `{sent: true}` for any number by design, and there is no seeded customer with an active booking
  in Postgres yet (that is Shared 5, the demo seed), so no challenge is created and no code exists
  to verify. The two steps are proven in Vitest against a mocked client and in Playwright against
  the real endpoint.
- `@axe-core/playwright` is not wired in. Technical/09 §8 asks for it; it is a dependency the
  brief did not authorise, so accessibility is currently held by the manual bar (labels, focus,
  icon+label chips, one `h1`, 44 px targets), not by an automated check.
- The workspace bundle is 1 MB (270 kB gzipped) in one chunk. Acceptable for an internal tool on
  office wifi; route-level `React.lazy` is the fix when it matters.
- `packages/ui`'s generated `types.ts` is exported but nothing consumes it yet — pages get types as
  they are ported.

### Deviations and why

1. **`.npmrc` with `legacy-peer-deps=true`.** v1 used yarn, which is lenient about peers. Under npm,
   `react-day-picker@8.10.1` (used by v1's `calendar.jsx`) declares peers `date-fns ^2||^3` and
   `react ^16||^17||^18`, while v1 pins `date-fns@^4` and React 19. Upgrading to
   `react-day-picker@9` is a breaking API change to a v1 file this task must not rewrite. One line
   in `.npmrc` reproduces what yarn was already doing. Remove it when `calendar.jsx` is ported.
2. **Three extra dev dependencies beyond technical/09 §2 + `openapi-typescript`:**
   `typescript-eslint` (its parser — ESLint cannot read a `.ts` file without it, and the customer
   app is entirely TypeScript), `eslint-plugin-react` (only `jsx-uses-vars` and `jsx-uses-react`;
   without them `no-unused-vars` reports every component used solely in JSX — 52 false positives in
   `App.js` alone; the plugin was already in v1's devDependencies), and `@testing-library/dom`
   (a peer of `@testing-library/react` that `legacy-peer-deps` stops npm from installing). All
   three are test/lint tooling, none ships in a bundle.
3. **The customer app moved React 18 → 19 and Vite 5 → 6.** Technical/09 §2 says React 19 and
   Vite 6; leaving it on 18 would have put two copies of React in the tree under one `packages/ui`.
4. **v1's three JSX-in-`.js` files are handled by a Vite plugin, not renamed.** In a production
   build `@vitejs/plugin-react` skips Babel entirely when no plugin needs it, and Vite's esbuild
   step gives `.js` the plain JS loader — so `App.js`, `index.js` and `lib/stageHelp.js` fail to
   parse. The 12-line `homeflow:jsx-in-js` plugin runs esbuild's JSX loader on them first. Renaming
   three files would also have worked; the brief said not to rename, and the plugin deletes itself
   when the last `.js` page is ported.
5. **`apps/workspace/src/lib/api.js` is a second axios client, not the shared one.** v1's routers
   are mounted bare at `/api/*` and do not speak the `{data, meta}` envelope, and 60 files call
   `const { data } = await api.get(...)`. One `createClient(baseURL, {unwrap: false})` keeps them
   working with the cookie while new code uses `api` from `@homeflow/ui`. Marked `ponytail:`.
6. **Shared components render against `.hf-*` CSS classes, not Tailwind utilities.** The two apps'
   Tailwind themes use different token names (`bg-background` vs `bg-bg`, `border-border` vs
   `border-line`), so one component set cannot use both. A `--ui-*` alias layer in `tokens.css`
   plus plain CSS in `ui.css` is the smallest thing that renders correctly in both skins, and it
   keeps every value a token.
7. **The ESLint token rule is `warn` on v1's tree.** 368 arbitrary lengths and 5 arbitrary hexes
   live in 68 v1 files that this task must not restyle. `error` for everything new, `warn` for the
   carried tree, so the debt is counted (532 warnings) without blocking the build. The block names
   its own exit condition.

## Item B — CDK (TASKS Vivek 9 · technical 10 §4, architecture §3)

### Why

`infra/` still held the 4 September shape: a `PlatformStack` with Cognito and an EventBridge bus,
and an `AppStack` with Aurora Serverless v2, a Lambda and an HTTP API behind a VPC with a NAT
gateway. Architecture §3 rejects every one of those choices, and for the same reason each time —
they solve problems this product will not have for years, they cost roughly $150/month against

### Deviations and why

1. **`homeflow_app`'s password is a documented one-off `ecs run-task`, not a custom resource.**

3. **A Secrets Manager interface VPC endpoint was added** (~$7/month, not in the §3.1 table, so the

4. **The RDS ingress rule lives in `ServiceStack`, not on `props.database.connections`.** The

5. **`infra/lib/*.ts` and `bin/*.ts` are ASCII-only.** These strings become AWS resource
   descriptions, and `ts-node` on this machine mangled `§` into `Â§` in the synthesised template.

### Why

## Run it by hand on this machine

```bash
# The stack (needed by everything below)
cd c:/Users/Vivek/Pranava-HomeFlow
npm run stack:dev                       # docker compose up -d --build
curl http://localhost:8001/health

# The two apps, in dev
npm install                             # once
npm run dev:workspace                   # http://localhost:5173  (sign in at /login)
npm run dev:customer                    # http://localhost:5174

# The two apps, served by the container by Host
docker compose up -d --build
#   http://localhost:8001/       -> the workspace
#   http://my.localhost:8001/    -> My Pranava Home
curl -H "Host: my.localhost:8001" http://localhost:8001/ | head -5

# Checks
npm run build && npm run typecheck && npm run lint && npm test
npm run test:e2e                        # Playwright, both apps, 3 breakpoints
npm run gen:api                         # regenerate packages/ui/src/api/types.ts
cd services/api && POSTGRES_HOST_PORT=5434 uv run pytest -q

# Infra (no AWS account is used or needed)
npm run synth
npm test -w @homeflow/infra
cd infra && npx cdk synth -c stage=staging

# CI, locally
npm run ci:local                        # all sixteen steps
npm run ci:local -- backend             # or frontend | contract | image | e2e | infra
```

To re-take the v1 page screenshots (Dashboard, Customer 360) you need v1's Mongo routers:

```bash
docker run -d --name hf-mongo-tmp -p 27017:27017 --network pranava-homeflow_default mongo:7
printf 'services:\n  api:\n    environment:\n      HOMEFLOW_V1_MONGO: "1"\n      MONGO_URL: "mongodb://hf-mongo-tmp:27017"\n      DB_NAME: "homeflow_v1"\n' > docker-compose.override.yml
docker compose up -d api && sleep 30
VITE_DEV_LOGIN=1 npm run dev -w @homeflow/workspace &
npm run e2e -w @homeflow/workspace
rm docker-compose.override.yml && docker rm -f hf-mongo-tmp && docker compose up -d api
```
